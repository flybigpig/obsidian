## 一、Input 模块调用链路

### 整体架构

```
硬件驱动 (内核层)
    ↓ (中断/epoll)
InputReader (读取事件，在独立线程中运行)
    ↓ 
InputDispatcher (分发事件，在独立线程中运行)
    ↓ (通过Socket/共享内存)
ViewRootImpl.WindowInputEventReceiver (App进程接收)
    ↓
DecorView → View树 (消费事件)
```

### 三大队列详解

| 队列 | 全名 | 含义 | 说明 |
|------|------|------|------|
| **IQ** | InputQueue / InboundQueue | **入队队列** | InputReader 读取原始事件后放入此队列，等待 InputDispatcher 处理 |
| **OQ** | OutboundQueue | **出队队列** | InputDispatcher 决定分发给哪个窗口后，待发送的事件暂存于此 |
| **WQ** | WaitQueue | **等待队列** | 事件已发送给目标窗口，等待 App 端 finish（完成处理）确认的事件 |

### 详细流程图

```
┌─────────────────────────────────────────────────────────────┐
│                      硬件输入设备                             │
│                   (触摸屏/键盘/鼠标)                          │
└──────────────────────┬──────────────────────────────────────┘
                       │ /dev/input/eventX
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                    InputReader 线程                         │
│  ┌───────────────────────────────────────────────────┐      │
│  │  EventHub (epoll_wait 监听设备节点)                 │      │
│  │       ↓                                            │      │
│  │  解析原始事件 → 封装为 NotifyKey/NotifyMotion       │      │
│  │       ↓                                            │      │
│  │  ★ 放入 IQ (mInboundQueue)                        │      │
│  └───────────────────────────────────────────────────┘      │
└──────────────────────┬──────────────────────────────────────┘
                       │ wake() 唤醒
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                  InputDispatcher 线程                       │
│  ┌───────────────────────────────────────────────────┐      │
│  │  1. 从 IQ 取出事件                                  │      │
│  │  2. 策略判断：找目标窗口 (findFocusedWindowTargets)  │      │

                       ▼
┌─────────────────────────────────────────────────────────────┐
│              App 进程 (ViewRootImpl)                        │
│  ┌───────────────────────────────────────────────────┐      │
│  │  WindowInputEventReceiver.onInputEvent()           │      │
│  │       ↓                                            │      │

│  │       ↓                                            │      │
│  │  DecorView.dispatchTouchEvent()                    │      │
│  │       ↓                                            │      │
│  │  View 树分发 → 消费                                 │      │
│  │       ↓                                            │      │
│  │  ★ 调用 finishInputEvent() 通知系统消费完毕         │      │
│  └───────────────────────────────────────────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

### 实际工作中的作用
- **ANR 排查**：触摸无响应时，查看 WQ 是否阻塞（App 未及时 finish）
- **事件丢失排查**：查看 OQ/WQ 大小，定位是分发还是消费侧问题
- **性能优化**：减少 InputDispatcher 的查找耗时

## 二、AIDL 与 Binder 通信

### AIDL 编译后的文件结构

```java
// 编译后生成的 Stub 类核心方法
public interface IMyService extends android.os.IInterface {
    // 服务端实现类
    public abstract class Stub extends android.os.Binder implements IMyService {
        // ★ 关键：asInterface - 客户端获取代理对象
        public static IMyService asInterface(android.os.IBinder obj) {
            if ((obj == null)) { return null; }
            // 先查询本地缓存
            android.os.IInterface iin = obj.queryLocalInterface(DESCRIPTOR);
            if (((iin != null) && (iin instanceof IMyService))) {
                return ((IMyService) iin); // 同进程，直接返回
            }
            return new Proxy(obj); // 跨进程，返回代理对象
        }
        
        // ★ Proxy 内部类 - 客户端的代理
        private static class Proxy implements IMyService {
            private android.os.IBinder mRemote;
            
            @Override  // 同步调用
            public String getData() throws android.os.RemoteException {
                android.os.Parcel _data = android.os.Parcel.obtain();
                android.os.Parcel _reply = android.os.Parcel.obtain();
                String _result;
                try {
                    _data.writeInterfaceToken(DESCRIPTOR);
                    // ★ transac 同步调用，会阻塞等待 reply
                    boolean _status = mRemote.transact(Stub.TRANSACTION_getData, 
                                                       _data, _reply, 0);
                    // ... 读取 _reply 结果 ...
                } finally {
                    _reply.recycle();
                    _data.recycle();
                }
                return _result;
            }
        }

        // ★ 服务端 onTransact 接收请求
        @Override
        public boolean onTransact(int code, android.os.Parcel data,
                                  android.os.Parcel reply, int flags) {
            switch (code) {
                case TRANSACTION_getData: {
                    data.enforceInterface(DESCRIPTOR);
                    String _result = this.getData(); // 调用服务端实现
                    reply.writeNoException();
                    reply.writeString(_result);
                    return true;
                }
            }
        }
    }
}
```

### Binder 同步 vs 异步

| 类型 | 标志位 | 行为 | 使用场景 |
|------|--------|------|----------|
| **同步** | `flags = 0` | 调用线程**阻塞**等待 `reply` 返回 | 普通方法调用，需要返回值 |
| **异步/oneway** | `flags = FLAG_ONEWAY` | 调用线程**不阻塞**，无需 `reply` | 回调通知、事件下发 |

#### 如何实现异步？
```java
// 方式1: oneway 关键字
oneway void notifyCallback(String msg); // AIDL声明

// 方式2: 手动设置 flags
mRemote.transact(code, data, null, IBinder.FLAG_ONEWAY);

// 方式3: 回调模式 (最常用)
interface ICallback { void onResult(String data); } // 定义回调接口
void asyncRequest(ICallback callback); // 方法传入回调对象
```

│  - Surface 创建时机不对                                │

## 七、动态壁纸 & 多屏壁纸

### 动态壁纸核心架构
```java
public class MyWallpaperService extends WallpaperService {
    @Override
    public Engine onCreateEngine() {
        return new MyEngine(); // 核心：返回自定义 Engine
    }
    
    private class MyEngine extends Engine implements SurfaceHolder.Callback {
        // Surface 创建回调
        @Override
        public void onSurfaceCreated(SurfaceHolder holder) {
            // 开始绘制循环
        }
        
        // 核心绘制方法
        @Override
        public void onSurfaceRedrawNeeded(SurfaceHolder holder) {
            Canvas canvas = holder.lockCanvas();
            try {
                // 绑定自定义绘制逻辑（视频/动画/粒子效果）
                drawFrame(canvas);
            } finally {
                holder.unlockCanvasAndPost(canvas);
            }
        }
        
        // 触摸事件处理
        @Override
        public void onTouchEvent(MotionEvent event) {
            // 壁纸可以响应触摸！这是 LiveWallpaper 特权
        }
    }
}
```

### 多屏壁纸实现思路
```
方案一：单 Engine 多 Surface（推荐）
┌──────────────┐     ┌──────────────┐
│  主屏 Display │     │  副屏 Display │
│  Surface #0   │     │  Surface #1   │
└──────┬───────┘     └──────┬───────┘
       │                    │
       └────────┬───────────┘
                ▼
        ┌───────────────┐
        │  同一个 Engine │
        │  统一管理绘制  │
        │  可做差异化   │
        └───────────────┘

方案二：双 Engine 实例（复杂场景）
- 主副屏各自一个 WallpaperService Connection
- 通过 Binder 同步状态/动画进度
```

**关键点**：
- 需要获取副屏的 `Display` 对象：`context.getSystemService(DisplayManager.class).getDisplay(displayId)`
- 为副屏创建独立的 `SurfaceView` 或直接操作 Surface
- 注意不同屏幕的分辨率/DPI 差异，做好适配

## 九、Oneway 异常深度解析

### 典型场景与机制

```
调用关系：
┌─────────────┐      oneway      ┌─────────────┐
│  调用方      │ ─────────────→  │  被调用方     │
│  (Client)   │  (不阻塞)       │  (Server)    │
└─────────────┘                 └──────┬──────┘
                                       │
                              Server 端处理
                              (Binder 线程池)
                                       │
                              ┌────────┴────────┐
                              ▼                 ▼
                        正常处理完成        处理异常/耗时过长
                                                   │
                                          ┌────────┴────────┐
                                          ▼                 ▼
                                    Transaction Too Large  Binder 线程耗尽
                                    (数据 > 1MB)           (所有线程被 oneway 占满)
```

### 两类典型异常：

| 异常类型 | 原因 | 解决方案 |
|---------|------|----------|
| **`TransactionTooLargeException`** | 单次 oneway 传输数据超过 ~1MB | 分片传输、用 Ashmem/FileDescriptor 传大数据 |
| **`DeadObjectException` / 无响应** | oneway 调用过频，Binder 线程池满（默认15个线程） | 控制频率、加队列限流、改用同步+异步线程池 |

### 谁调用谁？
```
常见场景：SystemServer → App 的 oneway 回调
例如：InputDispatcher → App 的 finishInputEvent 通道
      WMS → App 的 Window 回调
      NotificationManager → App 的 Notification 回调
```

   │                                                      │
   │ 瓶颈发现方式:                                         │

### Perfetto 发现瓶颈的方法：
- **Slice 过长**：主线程某函数执行时间 > 16ms
- **WakeLock 阻塞**：线程等待锁释放
- **GC 停顿**：ART GC 导致的主线程停顿
- **Binder 调用耗时**：跨进程同步调用过慢

## 十一、Proto Log 详解

### 为什么用 Proto Log？

```
传统日志的问题:
┌──────────────────────────────────────┐
│ SLOGI / ALOG* 直接打印字符串         │
│                                      │
│ 缺点：                                │
│ ① 发布版无法关闭 → 性能损耗          │
│ ② 字符串格式化在调用点执行 → 开销大  │
│ ③ 日志量大 → trace 文件爆炸          │
│ ④ 结构化差 → 后续分析困难            │
└──────────────────────────────────────┘

Proto Log 的优势:
┌──────────────────────────────────────┐
│ 编译期: .proto 定义 + 注解处理器       │
│   @ProtoLogGroup(ProtoLogGroup.TWM)  │
│   @ProtoLogMethod                   │
│   static void logWindow(...)        │
│                                      │
│ 运行时:                              │
│ ① UserBuild 自动变成 NO-OP (零开销)  │
│ ② 只记录参数 ID + 参数值（非字符串）  │
│ ③ 二进制高效存储                     │
│ ④ Perfetto 可视化时再格式化显示      │
└──────────────────────────────────────┘
```

### Proto Log 在 WMS 中的使用背景

```java
// 示例：WMS 中的 Proto Log 定义
@ProtoLogClass
@ProtoLogGroup(LogGroup.TWM, "Tag.WindowManager")
public class WindowManagerProtoLog {
    
    @ProtoLogMethod(
        message = "Window focus changed: window=%{window}, focused=%{boolean}",
        level = LogLevel.INFO
    )
    public static void logFocusChanged(WindowState win, boolean focused) {
        // UserBuild 下此方法体为空！零开销
    }
}
```

### 给谁看的？
- **Google 工程师**：bug report 中的 bugreport.txt / proto log
- **芯片厂商/ROM 开发者**：分析 WMS 窗口行为
- **Perfetto 用户**：图形化展示 WMS 事件流

### 没有Proto Log会怎样？
- UserBuild 无法获取 WMS 内部状态
- Bug report 文件过大（纯文本膨胀）
- 无法做精细的性能归因分析

## 十二、优先级反转 (Priority Inversion)

### 什么是优先级反转？

```
正常情况:
  High Priority Task (H) ─── 想执行，但等锁
  Medium Priority Task (M) ── 正常运行（占 CPU）
  Low Priority Task (L) ──── 持有锁，但被 M 抢占 CPU

反转发生:
  ┌────────────────────────────────────────────┐
  │  L 持有 Lock，正在执行临界区                  │
  │  H 到达，需要 Lock，阻塞等待 L               │
  │  M 到达，抢占 L 的 CPU（M > L）              │
  │  → L 无法释放锁 → H 被 M "间接"阻塞！        │
  │  → 高优先级任务被低优先级任务"拖累"           │
  └────────────────────────────────────────────┘
  
  结果: H 的有效优先级降到了 M 以下！（反转）
```

### 解决方案

| 方案 | 原理 | Android 中的应用 |
|------|------|------------------|
| **优先级继承 (PI)** | L 持有锁并被 H 等待时，临时提升 L 优先级到 H 级别 | Linux futex `FUTEX_LOCK_PI` |
| **优先级天花板 (PPC)** | 获取锁时就提升到天花板优先级 | 实时系统常用 |

### Perfetto 中的案例
- **主线程被 Binder 线程阻塞**：Binder 调用触发了低优先级后台线程持有锁
- **RenderThread 等待主线程**：主线程被低优先级任务占住
- **表现**：`sched_switch` 中看到高优先级线程在等低优先级线程释放锁

### 最近列表中从副屏"拿回"主屏的实现

```java
// 核心思路：Task 重组织 (Task Reparenting)

// 1. 在 RecentTasksUI 中捕获拖拽/点击手势
public class RecentsView extends FrameLayout {
    void onTaskClicked(Task.TaskKey taskKey, Display targetDisplay) {
        // 2. 获取目标 Task
        Task task = ActivityTaskManagerService.getTask(taskKey.id);
        
        // 3. 将 Task 从原 Display 移动到目标 Display
        // 这是核心 API 调用：
        ActivityTaskManager.getService().reparentTask(
            task.mTaskId,                    // 要移动的 Task
            targetDisplay.getRootTaskId(),   // 目标 Display 的 RootTask
            ON_TOP,                          // 放置位置
            true,                            // animate
            "Recents reparent",              // reason
            false                            // deferResume
        );
        
        // 4. 将该 Task带到前台
        ActivityManager.startActivityFromRecents(
            task.mTaskId, 
            bundleOf(KEY_DISPLAY_ID to targetDisplay.displayId)
        );
    }
}

// 底层 WMS 调用链:
// ATMS.reparentTask()
//   → RootWindowContainer.reparentTask()
//     → Task.reparent() 
//       → DisplayContent.addChild() / moveToDisplay()
//       → SurfaceControl.Transaction.reparent(新Display的Surface)
//       → 更新 Configuration（新屏幕尺寸/DPI）
//       → 重新 relayout 窗口
```
