## 阶段 0：开机时构造并注册 Lifecycle

SystemServer 先启动 ATMS，再把 `atm` 桥接进 AMS：

```660:663:frameworks/base/services/java/com/android/server/SystemServer.java
ActivityTaskManagerService atm = mSystemServiceManager.startService(
        ActivityTaskManagerService.Lifecycle.class).getService();
mActivityManagerService = ActivityManagerService.Lifecycle.startService(
        mSystemServiceManager, atm);
```

`Lifecycle.startService(ssm, atm)` 先把 `atm` 存进静态 `sAtm`，再 `ssm.startService(Lifecycle.class)`。回顾上一轮看到的机制：`SystemServiceManager.startService(Class)` 用反射 `Constructor(Context.class)` 实例化 `Lifecycle`，构造里 `mService = new ActivityManagerService(context, sAtm)` 创建真正的 AMS，随后立即调用 `onStart()` 并把它加入 `mServices` 列表。

## 阶段 1：onStart → 注册 binder 句柄

`Lifecycle.onStart()` 转发到 `mService.start()`，AMS 在其中通过 `publishBinderService("activity", mBinder)` 把自己的 Binder 桩注册出去。基类 `SystemService.publishBinderService` 最终调用：

```236:236:frameworks/base/services/core/java/com/android/server/SystemService.java
ServiceManager.addService(name, service, allowIsolated, dumpPriority);
```

`ServiceManager.addService("activity", ...)` 这一行本身**就是一次 binder 调用**（从 `system_server` 进程发向 binder 上下文管理器 servicemanager，句柄固定为 0，即 `BC_TRANSACTION`）。注册动作到此进入 SELinux 的管控范围。

## 阶段 2：servicemanager 侧三道 SELinux 关卡（注册期）

servicemanager 收到 `addService` 请求后，要做三件事来核定这次注册是否合法——正好对应第一轮讲的三处文件：

第一关，名字映射类型（`service_contexts`）：

```3:3:c:/D/android_project/cells-android10/system/sepolicy/private/service_contexts
activity                                  u:object_r:activity_service:s0
```

servicemanager 据此知道名字 `activity` 对应类型 `activity_service`。

第二关，类型与属性声明（`service.te`）：

```43:43:c:/D/android_project/cells-android10/system/sepolicy/public/service.te
type activity_service, app_api_service, ephemeral_app_api_service, system_server_service, service_manager_type;
```

`activity_service` 因此带有 `system_server_service`、`app_api_service` 等属性标签，这些属性决定了"谁能 add / 谁能 find"。

第三关，域权限（域 .te）：AMS 运行在 `system_server` 域，`system_server.te` 里有：

```703:703:c:/D/android_project/cells-android10/system/sepolicy/private/system_server.te
add_service(system_server, system_server_service);
```

查 `add_service` 宏定义：

```614:617:c:/D/android_project/cells-android10/system/sepolicy/public/te_macros
define(`add_service', `
  allow $1 $2:service_manager { add find };
  neverallow { domain -$1 } $2:service_manager add;
')
```

它展开为 `allow system_server system_server_service:service_manager { add find };` 加一条 `neverallow` 禁止其他任何域 `add`。因为 `activity_service` 携带 `system_server_service` 属性，这条 `allow` 正好覆盖它，于是注册被放行，servicemanager 在内部把 `"activity" → binder句柄` 记下。至此 App 端将来才能查到这个名字。

## 阶段 3：开机阶段推进（onBootPhase）

注册完成后，`SystemServiceManager.startBootPhase(phase)` 会遍历所有已注册服务逐个回调 `onBootPhase`。`Lifecycle.onBootPhase` 把阶段写进 `mService.mBootPhase`，并在 `PHASE_SYSTEM_SERVICES_READY`(500)、`PHASE_ACTIVITY_MANAGER_READY`(550)、`PHASE_THIRD_PARTY_APPS_CAN_START`(600) 触发 BatteryStats、ActiveServices、`startBroadcastObservers()`、PackageWatchdog 等子模块就绪。也就是说，要到这些阶段之后，AMS 才真正具备对外服务能力。

## 阶段 4：App 端发现服务（find 关卡再次生效）

App 调用 `Context.getSystemService(ACTIVITY_SERVICE)` → `SystemServiceRegistry` 返回 `ActivityManager`（Manager 封装），其内部通过 `ServiceManager.getService("activity")` 拿到 binder 代理（`IActivityManager`）。`getService` 同样是一次发往 servicemanager 的 `BC_TRANSACTION`。

这一步的 SELinux 检查是"find"而非"add"：客户端域（如普通 App 的 `untrusted_app_all`）需要 `find` 权限：

```100:100:c:/D/android_project/cells-android10/system/sepolicy/private/untrusted_app_all.te
allow untrusted_app_all app_api_service:service_manager find;
```

由于 `activity_service` 带 `app_api_service` 属性，普通 App 被允许 `find` 到它；servicemanager 于是把 `activity_service` 对应的 binder 句柄返回给 App 进程。

## 阶段 5：跨进程调用（binder_call 关卡 + 内核路径）

App 调用 `activityManager.startActivity(...)`，代理把参数打包成 `Parcel`，通过 `/dev/binder` 发出 `BC_TRANSACTION`。进入内核后走第一轮的 binder 路径：`binder_transaction()` 做事务转发，最终在 `system_server` 的 binder 线程上投递 `BR_TRANSACTION`，AMS 的 Binder 桩 `onTransact()` 解包并真正执行方法。

这里还有一道 SELinux 关卡 `binder_call`：客户端域必须被允许向 `system_server` 发起 binder 调用。宏定义如下：

```381:387:c:/D/android_project/cells-android10/system/sepolicy/public/te_macros
define(`binder_call', `
allow $1 $2:binder { call transfer };
allow $2 $1:binder transfer;
allow $1 $2:fd use;
')
```

对 App 而言即 `binder_call(appdomain, system_server)` → `allow appdomain system_server:binder { call transfer };`，它决定了这次事务能否真正被投递到 `system_server`。

## 阶段 6：返回结果

AMS 执行完毕，结果经 `BC_REPLY`/`BR_REPLY` 沿原路返回 App 的 binder 线程，代理解包后 App 拿到返回值，一次完整 IPC 闭环结束。

## 全链路一图概括

开机构造（`Lifecycle` 反射实例化 AMS，`onStart` 触发 `start()`）→ 注册（`publishBinderService` → `ServiceManager.addService`，servicemanager 经 service_contexts 定类型、service.te 定属性、system_server.te 的 `add_service` 宏放行）→ 阶段推进（`onBootPhase` 各级就绪）→ 客户端发现（`getService`，经 `app_api_service:find` 放行）→ 跨进程调用（`BC_TRANSACTION` → 内核 `binder_transaction` → `BR_TRANSACTION`，经 `binder_call` 宏放行）→ 返回（`BR_REPLY`）。

一句话：第一轮的 binder 内核路径（`BC_TRANSACTION → binder_transaction → BR_TRANSACTION`）是"运输通道"，而 service_contexts / service.te / 域 .te 这套 SELinux 规则是"通行证检查"，`Lifecycle` 这套 `SystemService` 机制则是把 AMS 挂上通道、领到通行证、并随开机阶段逐步放权的"调度员"。三者在 `system_server` 进程里交汇，才让一个 App 能安全地跨进程调到 ActivityManagerService。
