## 一、开机流程

```
Boot ROM → BootLoader → Linux Kernel → init进程
    → Zygote → SystemServer → 各种Service → Launcher
```

### 为什么需要 init 启动 Zygote，不能直接启动 SystemServer？

**核心原因：Zygote 是所有 Java 进程的孵化器**

- **Zygote 预加载了所有 Java 核心类库和资源**（如 `android.*` 包、主题资源等），App 进程 fork 自 Zygote 可以直接复用，**大幅加速启动**
- **SystemServer 也是一个 Java 进程**，它也是从 Zygote fork 出来的，而不是直接启动的
- 如果直接启动 SystemServer：
  - 每次都要重新加载 Java 虚拟机、核心类库，**启动极慢**
  - 每个 App 启动也要重新加载，**内存占用剧增**
- 所以流程是：`init → Zygote → fork SystemServer → fork 其他 App`

## 二、开机性能优化 & 开机动画

### 优化思路

| 方向 | 方案 |
|------|------|
| **并行化** | 将 init.rc 中串行的 service 启动改为并行，减少等待 |
| **精简 Service** | 将非必须的 Service 延迟启动或按需启动（Lazy Service） |
| **预加载优化** | Zygote 预加载只保留核心类，减少无谓加载 |
| **IO 优化** | 使用 `f2fs` 文件系统、文件预读、Block 对齐 |
| **SElinux 策略精简** | 减少不必要的权限检查 |

### 开机动画能否提前结束？

**可以，但需要策略**：

我的方案：
```
1. 关键Service就绪 → 动画透明过渡
2. 监听 SystemServer 中核心 Service 注册完成信号
3. 不需要等待全部完成，而是：
   - ActivityManagerService 就绪
   - WindowManagerService 就绪
   - Launcher 进程已创建
   → 即可结束动画，非核心 Service 后台延迟启动
```

### FallbackHome 是否可以去除？

**分情况讨论**：

| 场景 | 判断 |
|------|------|
| 有默认 Launcher | **可以去**，直接启动 Launcher |
| 无预装 Launcher | **不能去**，FallbackHome 确保用户能看到 UI |

**市场方案调研**：
- **Google Pixel**：保留 FallbackHome 作为安全网
- **华为 EMUI**：去除了 FallbackHome，直接启动系统 Launcher，开机速度快约 **200-500ms**
- **小米 MIUI**：用自定义的 `BootCompleteReceiver` 替代

**建议**：如果系统有固化 Launcher（不可卸载），可以去除 FallbackHome；否则保留。

## 三、Input 模块调用链路

```
触摸/按键物理事件
    ↓ (硬件中断)
Linux Kernel Input Subsystem (EventHub)
    ↓ (epoll 读取)
InputReader (事件解析)
    ↓ (放入)
IQ → InputClassifier → OQ
    ↓
InputDispatcher (事件分发)
    ↓ (寻找焦点窗口)
WQ (等待队列)
    ↓ (Socket Pair 发送)
App 进程 (ViewRootImpl)
    ↓
View 事件分发 (dispatchTouchEvent)
```

### IQ、OQ、WQ 含义

| 队列 | 全称 | 作用 |
|------|------|------|
| **IQ** | Input Queue | **原始事件输入队列**。InputReader 将从 EventHub 读取的 RawEvent 放入此队列 |
| **OQ** | Output Queue | **分类后输出队列**。经过 InputClassifier 处理后的事件放入此队列，等待 InputDispatcher 取走 |
| **WQ** | Wait Queue | **等待分发队列**。InputDispatcher 将要分发给目标窗口的事件放入此队列，等待 App 处理完成并返回处理结果 |

### Key 事件分发流程

```
InputDispatcher → WindowManagerService(找焦点窗口)
    → Socket Pair 写入 → App 端接收
    → ViewRootImpl → DecorView → Activity.dispatchKeyEvent
    → Activity.onKeyDown/Up
    → 结果返回 InputDispatcher
```

## 四、冷启动 vs 热启动

| 对比项 | 冷启动 | 热启动 |
|--------|--------|--------|
| **进程** | 不存在，需新建 | 已在后台存活 |
| **Zygote** | 需要 fork | 不需要 |
| **Application** | 重新创建 | 复用 |
| **Activity** | 重建 | 通过 `onNewIntent` 或恢复 |
| **耗时** | **数秒** | **毫秒级** |
| **关键瓶颈** | `Application.onCreate` + `Activity.onCreate` | Activity 生命周期恢复 |

## 五、窗口状态流转

```
ADDED        →   REMOVED
  ↓                  ↓
WAITING_FOR_WINDOW  →  FINISHED
  ↓
HAS_SURFACE (可见)
  ↓
HIDDEN (不可见)
```

主要状态：

| 状态 | 含义 |
|------|------|
| `ADDED` | Window 已添加到 WMS |
| `WAITING_FOR_WINDOW` | 等待窗口 Surface 创建 |
| `HAS_SURFACE` | Surface 已创建，窗口可见 |
| `HIDDEN` | 窗口被隐藏 |
| `REMOVED` | 窗口被移除 |
| `FINISHED` | 窗口彻底销毁 |

## 六、ANR 处理

### ANR 类型

| 类型 | 触发条件 |
|------|----------|
| **Input ANR** | 输入事件 5s 未响应 |
| **Broadcast ANR** | 前台广播 10s / 后台广播 60s 未完成 |
| **Service ANR** | 前台 20s / 后台 200s |
| **ContentProvider ANR** | 超时未发布 |

### 分析 & 解决 ANR

```
1. 获取 /data/anr/traces.txt
2. 定位主线程堆栈
3. 常见原因：
   - 主线程 IO 操作（SharedPreference写入、文件读写）
   - 主线程锁等待（死锁）
   - Binder 调用阻塞
   - 频繁 GC
   - 布局过于复杂（过度绘制）
4. 方案：
   - IO 操作移至子线程
   - 使用 SparseArray 替代 HashMap（减少锁）
   - 使用异步 Binder
   - 优化布局层级
```

## 七、Binder 一次拷贝

```
客户端
  ↓ 调用 transact()
  ↓ 用户空间
  ↓ copy_from_user() ← 第一次拷贝（用户态→内核态）
  ↓
Binder 驱动 (内核空间)
  ↓ 通过 mmap 共享内存
  ↓ 不需要第二次拷贝（内核态→目标用户态） ← ★
  ↓
服务端
  ↓ 直接读取共享内存
```

**为什么只有一次拷贝？**
- Binder 采用 **mmap** 映射机制，在内核空间和服务器端用户空间共享一块内存
- 数据从客户端用户空间 **拷贝到内核空间一次**，然后通过 mmap **直接映射到服务端用户空间**，无需第二次拷贝
- 对比传统 IPC（Socket/Pipe）：需要 **两次拷贝**（用户→内核，内核→目标用户）

## 八、WMS 层级结构树

```
DisplayContent
  └── TaskDisplayArea (0: 默认, 1: 分屏, ...)
      └── Task
          └── TaskFragment
              └── WindowContainer (ActivityRecord)
                  └── WindowState
                      └── SurfaceControl
```

### 查看命令

```bash
# dump 窗口层级
adb shell dumpsys window windows

# dump 窗口层级树
adb shell dumpsys window visible

# 特殊命令
adb shell dumpsys window -a
```

### TaskDisplayArea 的作用

- **概念**：任务的容器，相当于屏幕上的不同显示区域
- **作用**：支持多窗口、分屏、自由窗口等场景
- **子节点**：**Task**（任务栈）
- **意义**：没有它之前，单个显示屏只能有一个任务栈；有了它，可以在一屏上同时展示多个 Task（分屏、画中画）

### WindowToken 的作用

- **作用**：窗口的访问凭证，用来标识一个窗口的"身份组"
- **为什么叫 Token**：Token 是"令牌"的含义，具备以下特性：
  - **唯一性**：一个 Token 代表一组相关窗口
  - **权限验证**：只有持有 Token 的组件才能添加/操作窗口
  - **生命周期绑定**：Token 与 WindowManager 的操作请求绑定，Token 失效则窗口自动销毁
- **具体场景**：
  - Activity 启动时 AMS 会创建一个 `ActivityRecord` 作为 Token
  - 然后通过这个 Token 向 WMS 添加窗口
  - 如果 Token 不匹配，WMS 拒绝操作

## 九、Proto Log 在 WMS 中的应用

### 为什么用 Proto Log？

| 对比 | 普通 Log | Proto Log |
|------|---------|-----------|
| 格式 | 纯文本 | **结构化 Protobuf 二进制** |
| 可解析性 | 需正则解析 | **可直接反序列化成对象** |
| 体积 | 大 | 小（二进制压缩） |
| 分析效率 | 人工逐行看 | **工具自动化分析，秒级定位** |

### Proto 工程背景

- **WMS dump 内容极其庞大**（几百 K ~ 几 MB）
- 普通文本 dump 难以对比前后差异
- Proto Log 可以用 **Diff 工具直接对比**两个时间点的窗口状态
- **给谁看**：主要是 **框架工程师和稳定性测试团队** 用于调试窗口异常问题

### 有 Proto 和没有 Proto 的区别

| 场景 | 没有 Proto | 有 Proto |
|------|-----------|---------|
| 窗口泄漏排查 | 手动翻几百行 log | `diff protocol_buffer` 秒定位 |
| 窗口位置异常 | 肉眼对比坐标 | 可视化工具回放 |
| 多窗口兼容 | 每个 case 手动排查 | 自动化对比回归测试 |
