## 二、单链表基础

## 2.1 数组 vs 链表

数组 = 电影院一排座位：按号找人 O(1)，但中间插人所有人往后挪 O(n)。

链表 = 寻宝游戏：每个线索写着"下一站在哪"，找第 k 个必须从头走 O(n)，但插入只需改前后指向 O(1)。

|   操作   |   数组    |        链表         |
|--------|---------|-------------------|
| 按下标访问  |  O(1)   |       O(n)        |
|  头部插入  | O(n) 搬移 |       O(1)        |
|  有序插入  | O(n) 搬移 | O(n) 查找 + O(1) 插入 |
| 删除已知节点 | O(n) 搬移 |   O(1)（已知 prev）   |
|   内存   | 连续，可能浪费 |      分散，按需分配      |
| 缓存友好性  | 高（连续内存） |      低（分散内存）      |

> **一句话**：数组擅长读，链表擅长写。

## 三、MessageQueue 中的单链表

> **通俗理解**：把 MessageQueue 想象成一个**奶茶店的排队系统**——Message 是顾客（身上写着"几点到的"和"谁叫的号"），MessageQueue 是一条按预约时间排好序的队伍，Looper 是店员不停地从最前面叫号。

## 3.1 Message 即节点（侵入式链表）

```perl
public final class Message {
```

Message 同时是数据载体和链表节点，不需要额外 Node 包装。好处是零额外内存分配，代价是一个 Message 同一时间只能在一条链表中。

> **通俗理解**：普通链表是"信封装信"——Node 是信封，数据是里面的信。而 Message 是"明信片"——数据和 `next` 指针直接写在自己身上，省掉了信封。

MessageQueue 只持有头指针：

```perl
Message mMessages;  // 链表头，始终是 when 最小（最早执行）的消息
```

## 3.2 有序插入 — enqueueMessage()

```java
boolean enqueueMessage(Message msg, long when) {
```

对应基础操作：有序插入（按 when 升序）。

关键细节：when < p.when用严格小于（不是<=），when 相同的消息不会插到前面去，保证FIFO。

```csharp
发送: msg1(when=T) → msg2(when=T) → msg3(when=T)
```

时间复杂度：O(n)，但实际消息量通常几十到几百，且大多数消息 when 相近插在尾部附近。

> **通俗理解**：新顾客来了不是直接排最后，而是**按预约时间插到正确位置**。队伍是 `[10:00] → [10:05] → [10:10]`，来了个 `[10:03]` 的就插到 10:00 和 10:05 中间。两人预约时间一样？用 `<` 不用 `<=`，意味着**同时间的不能插队到前面去**，谁先来谁排前面。

## 3.3 取头节点 — next()

```csharp
Message next() {
```

对应基础操作：

|   逻辑   |         链表操作          | 复杂度  |
|--------|-----------------------|------|
| 正常取消息  |         删除头节点         | O(1) |
| 同步屏障模式 |      遍历找第一个异步消息       | O(n) |
|  延迟消息  | 不取出，算 timeout 给 epoll |  —   |

> **通俗理解**：店员永远从**队伍最前面**叫号——O(1) 超快。但碰到**同步屏障**（一个 `target == null` 的特殊标记）就进入"VIP 通道"模式：跳过所有普通顾客，专门往后找 VIP（异步消息）优先处理。这就是 Choreographer 的 UI 绘制消息能插队执行的原因。如果队头顾客的预约时间还没到，店员就不叫号，先休息（epoll 等待），到点了再叫。

## 3.4 按条件批量删除 — removeMessages()

```typescript
void removeMessages(Handler h, int what, Object object) {
```

对应基础操作：按条件批量删除。分两阶段是因为删头节点（改 mMessages）和删中间节点（改 prev.next）逻辑不同。

removeCallbacksAndMessages(null)传 null 时清空整条链表——在onDestroy中防止 Handler 内存泄漏。

> **通俗理解**：某个 Handler 要退号，需要把它发的所有消息全删掉。为什么要分两个 while 循环？因为**删队头**和**删中间的人**动作不同：删队头是直接把 `mMessages` 头指针往后挪；删中间是让前一个人"跳过"被删的人指向下一个。两种情况写法不同，所以分开处理。

## 3.5 对象池 — Message 回收复用

```perl
public final class Message {
```

数据结构本质：用单链表实现的栈（LIFO），头插头取，O(1)。

为什么用 LIFO 不用 FIFO？最近回收的 Message CPU 缓存更热，且栈用单链表实现最简单，不需要维护尾指针。

> **通俗理解**：Message 用完不扔掉，清空数据后放进一个"回收站"（最多存 50 个）。下次需要新 Message 时先从回收站里拿，拿不到再新建——省去反复创建对象的开销。回收站用的是**栈**的方式（后进先出）：最后放进去的最先拿出来，因为最近刚回收的对象在 CPU 缓存里还是"热"的，用起来更快。
> 
> ```
> 回收（头插法）：新回收的 → 池头 → 旧的 → ...
> ```

## 3.6 为什么选链表不选数组

|   维度   |        链表         |  数组 / PriorityQueue   |
|--------|-------------------|-----------------------|
|  有序插入  | O(n) 找位置 + O(1) 插 | O(log n) 找 + O(n) 搬移  |
|  取头消息  |       O(1)        | O(1) 堆顶 + O(log n) 调整 |
| 按条件删除  |    O(n) 遍历直接删     |   O(n) 查找 + O(n) 搬移   |
| 同步屏障遍历 |     天然支持顺序遍历      |       堆结构无法按序遍历       |
|   内存   |     无需预分配、无扩容     |        需要扩容拷贝         |

核心原因：MessageQueue 需要频繁的按条件删除和同步屏障遍历，链表在这两个操作上更自然。消息数量通常不大，O(n) 插入的实际开销很小。

> **一句话**：消息量不大（几十到几百），链表的 O(n) 完全够用，而它在删除和按序遍历上比数组/堆自然得多——改个指针就行，不用搬家。

## 4.4 找环入口（LeetCode 142）

第一次相遇后，一个指针回到 head，两指针同速走，再次相遇就是环入口。

```javascript
ListNode detectCycle(ListNode head) {
```

数学证明：设 head 到入口 = a，入口到相遇 = b，相遇到入口 = c。 fast 走了 2(a+b) = a+b+nC → a = nC-b = (n-1)C+c。 从 head 走 a 步 = 从相遇点走 c + (n-1) 圈 → 在入口相遇。

## 面试回答模板

> **问**：MessageQueue 为什么用链表？ 
> 
> **答**：MessageQueue 的核心操作是按 when 有序插入、取头消息、按条件批量删除。链表插入删除只改指针不搬移元素，且支持同步屏障的顺序遍历。消息数量通常几十到几百，O(n) 插入开销很小。如果用堆（PriorityQueue），虽然插入 O(log n) 更快，但无法按序遍历（屏障逻辑失效），按条件删除也需要 O(n) 查找 + O(n) 搬移，综合不如链表。
