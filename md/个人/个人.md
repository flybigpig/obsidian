### **一、网络与跨进程通信（IPC）**

#### **1. socketpair 对比 socket 的区别和关系**

- **socket**：  
    传统套接字，用于**不同主机间的进程通信**（基于 TCP/UDP），需指定 IP 地址和端口号，支持流式（SOCK_STREAM）和数据报（SOCK_DGRAM）类型。
- **socketpair**：  
    套接字对，用于**同一主机内的进程通信**（仅限本地），通过`AF_UNIX`协议族创建，返回两个相互连接的文件描述符（fd1 和 fd2），数据可在两者间双向传输，类似管道（Pipe）但支持全双工。
- **核心区别**：
    
    |特性|socket|socketpair|
    |---|---|---|
    |通信范围|跨主机 / 本地|仅限本地|
    |地址类型|IP + 端口或 UNIX 路径|UNIX 路径（隐式创建）|
    |连接方式|需主动 connect ()|自动连接|
    |典型场景|网络服务|本地进程间通信|
    

#### **2. socketpair 如何实现跨进程通信？**

socketpair 创建的两个 fd 属于**同一进程**，若需跨进程通信，需通过以下步骤：

  

1. **fork 子进程**：在父进程中创建 socketpair 后，通过`fork()`复制进程空间，子进程继承这两个 fd。
2. **文件描述符传递**：父进程和子进程分别使用其中一个 fd（如父用 fd1，子用 fd2），通过读写操作实现双向通信。
    - 本质：利用 UNIX 域套接字的本地通信能力，通过进程间共享 fd 实现跨进程数据传输。

### **二、Binder 通信核心机制**

#### **3. Binder oneway 与非 oneway 的区别？oneway 需注意什么？**

- **区别**：
    
    |特性|oneway（单向）|非 oneway（双向）|
    |---|---|---|
    |响应机制|无返回值，无需等待|需等待服务端返回结果|
    |线程模型|客户端可在任意线程调用|客户端需在 Binder 线程或异步线程调用|
    |适用场景|通知类操作（如日志上报）|需结果的交互（如查询数据）|
    
- **oneway 注意事项**：
    1. 服务端处理 oneway 请求时**无需返回 Parcel**，若调用`transact()`时未标记`FLAG_ONEWAY`，可能导致客户端阻塞。
    2. 避免在 oneway 请求中执行耗时操作，否则可能阻塞服务端 Binder 线程池。

#### **4. 不同进程的 Binder 客户端请求同一服务时，handle 是否相等？**

- **不相等**。
    - `handle`是客户端对服务端 Binder 对象的**本地引用句柄**，由 Binder 驱动分配，仅在**当前进程内唯一**。
    - 不同进程的客户端通过`ServiceManager`获取同一服务时，驱动会为每个进程生成独立的 handle，因此值不同，但均指向同一服务端 Binder 实体。

#### **5. 为何用 Binder 对象作为 token？利用了什么原理？**

- **原理**：Binder 对象的**唯一性**和**跨进程标识**特性。
    - 每个 Binder 实体在系统中具有唯一的`nodeid`，跨进程传递时，token（即 Binder 对象）可唯一标识一个服务或上下文，避免伪造（类似内存地址空间隔离）。
    - 典型场景：Activity 启动时用 TaskRecord 的 Binder 作为 token，确保权限校验的唯一性。

### **三、系统调度与 ANR 分析**

#### **6. Input 事件流程**

1. **InputReader 线程**：
    - 从内核读取输入设备事件（如触摸、按键），封装为`MotionEvent`或`KeyEvent`。
2. **InputDispatcher 线程**：
    - 将事件分发给目标窗口（通过`WindowManagerService`获取焦点窗口），调用应用的`InputEventReceiver`。
3. **应用层处理**：
    - 事件通过`Looper`传递至主线程，经`ActivityThread`分发到`Activity`的`dispatchTouchEvent`等回调。

#### **7. ANR 触发条件与场景**

- **触发条件**：主线程（UI 线程）在特定时间内未处理完消息：
    - **输入事件（Input）**：5 秒内未响应屏幕触摸 / 按键事件。
    - **Service 超时**：前台 Service 20 秒、后台 Service 200 秒未执行完毕。
    - **Broadcast 超时**：前台广播 10 秒、后台广播 60 秒未处理完毕。
- **具体问题分析**：
    - **问题 19**：`onResume`中耗时 10 秒会触发 ANR，因主线程被阻塞，无法处理输入事件和消息循环。
    - **问题 20-21**：按钮点击不松手（持续触发触摸事件）或延时操作，若阻塞主线程超过 5 秒，会触发输入型 ANR。

#### **8. 冻屏问题分析思路**

1. **抓取系统日志**：
    - `adb shell dumpsys gfxinfo <package>`：查看帧率（FPS）是否异常（低于 16fps 可能卡顿）。
    - `adb shell dumpsys SurfaceFlinger --latency <window>`：分析 Surface 合成延迟。
2. **性能工具追踪**：
    - **Perfetto**：记录主线程、RenderThread 的耗时操作，定位 UI 渲染瓶颈（如主线程布局耗时、GPU 渲染延迟）。
    - **Systrace**：分析 CPU 调度、Binder 通信延迟是否导致线程阻塞。
3. **代码层面排查**：
    - 检查是否在主线程执行耗时操作（如 IO、网络请求），是否存在锁竞争或死锁。

### **四、系统启动与进程管理**

#### **9. 开机阶段耗时查看**

- **工具**：
    1. **logcat 搜索启动日志**：
        - `adb logcat | grep "system_server ready"`：计算从开机到 SystemServer 启动完成的时间。
        - `adb logcat | grep "ActivityManagerService"`：查看 AMS 启动耗时。
    2. **使用 Perfetto 追踪**：
        - 录制启动阶段的系统追踪数据，分析`init`进程、Zygote、SystemServer 的启动耗时分布。

#### **10. Native 进程开机启动方法**

1. **通过 init 进程配置**：  
    在`/system/core/rootdir/init.rc`中添加服务配置，如：
    
    rc
    
    ```rc
    service native_daemon /system/bin/native_process  
        class main  
        user root  
        group root  
        critical  
    ```
    
      
    - `class main`：随 init 进程启动时创建。
    - `critical`：若进程崩溃，init 会立即重启。
2. **通过 Zygote 孵化**：  
    编写 JNI 层代码，在 Zygote 启动时通过`fork()`创建 Native 进程（需处理信号和资源隔离）。

    3. 若命令不存在，检查模块编译配置（如`Android.mk`中是否包含`LOCAL_C_INCLUDES`或`LOCAL_SRC_FILES`）。

#### **12. Perfetto 线程状态颜色**

- **绿色**：线程处于`RUNNING`状态（正在执行）。
- **黄色**：线程处于`RUNNABLE`状态（就绪，等待 CPU 调度）。
- **红色**：线程处于`BLOCKED`状态（阻塞，如等待锁或 IO）。
- **灰色**：线程处于`SLEEPING`状态（休眠，如`Thread.sleep()`）。

### **六、实战问题延伸**

#### **13. 车载多窗口实现思路**

- **单屏多窗口**：  
    通过 SurfaceFlinger 的`Layer`分层机制，将不同应用的窗口（如导航、媒体播放）渲染到同一物理屏幕的不同区域，利用`DisplayContent`管理各窗口的坐标和尺寸。
- **多屏显示**：
    1. 为每个屏幕创建独立的`Display`对象，通过`DisplayManager`管理。
    2. 使用`ActivityManagerService`的`resizeTask()`将任务分配到指定屏幕的`Display`上。
    3. 各屏幕的 SurfaceFlinger 实例同步渲染对应的 Layer 层级。
