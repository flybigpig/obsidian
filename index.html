    • ▶
      1.1 Bootloader & Kernel 阶段
      • ·
        Bootloader (aboot/lk)
        初始化 DDR/存储/显示，加载 boot.img（kernel+dtb）；校验 AVB vbmeta（模块 25.2）；传递 cmdline（androidboot.*）；lk 定制点：logo、按键组合（fastboot/recovery）
      • ·
        Kernel 启动
        start_kernel → rest_init（创建 kernel_init + kthreadd）→ 解析 DTB 设备树（/proc/device-tree，模块 17.2）→ 初始化驱动模型/内存管理 → 挂载 rootfs/tmpfs → 启动 init (PID 1)
      • ·
        内核启动参数 (cmdline / bootconfig)
        androidboot.* 系列：androidboot.selinux（permissive/enforcing）· androidboot.slot_suffix（_a/_b，模块 24.1）· androidboot.verifiedbootstate（AVB 状态，模块 25.2）· androidboot.hardware；Android 12+ 支持 bootconfig（/proc/bootconfig，替代部分 cmdline）
      • ·
        initcall 驱动加载层次
        kernel_init → do_basic_setup → do_initcalls：early_initcall → core → postcore → arch → subsys → fs → device_initcall（platform_driver_register 的驱动 probe 多在此，模块 17.1）；顺序决定外设枚举时序，乱序改 initcall level
      • ·
        ramdisk 与 rootfs 挂载链
        boot.img 内 first_stage_ramdisk；AOSP 10+ System-as-Root (SAR)：system 分区直接作 rootfs（ramdisk 仅保留第一阶段）；init_first_stage 经 fs_mgr 挂载 /system /vendor（fstab 见模块 22.5）；SAR 后 system 只读防篡改（AVB）
      • ·
        boot.img / vendor_boot 结构
        boot header v3/v4：AOSP 11+ vendor_boot 分离（vendor_ramdisk + dtb 独立）；mkbootimg 打包 · fastboot flash boot/vendor_boot；dtbo 分区独立（设备树 overlay，模块 17.2）；boot 分区改动与 AVB 签名联动（模块 25.2）
    • ▶
      1.2 init 进程 system/core/init
      • ·
        First Stage Init
        内核解压 first_stage_ramdisk → 执行 /init（init_first_stage）→ 挂载 tmpfs/dev、等待 /dev/block 就绪（fs_mgr 解析 fstab，模块 22.5）→ 挂载 /system /vendor → 加载 sepolicy → 切换 Second Stage
      • ·
        Second Stage Init
        解析 *.rc 文件、启动属性服务、触发 on early-init / init / post-fs / boot
      • ·
        关键 rc 文件
        核心：init.rc（平台通用）· init.<hw>.rc（设备专属，如 init.ranchu.rc）· ueventd.rc（设备节点规则，模块 1.2）· vendor/odm 自定义 rc（/vendor/etc/init/，车载定制放此，遵循 Treble 隔离）
      • ·
        服务启动 (Service)
        init.rc 中 service <name> <path> <args> 定义守护进程；class core/main 分组（zygote/servicemanager/surfaceflinger 属 core，随系统重启）；onrestart 依赖链（zygote 崩 → 重启关键服务）；seclabel 指定 SELinux 域（模块 15.4）
      • ·
        属性服务 (property service)
        property_set()/property_get()；共享内存 /dev/__properties__（所有进程 mmap 共享）；persist.* 属性落盘 /data/property；写入经 SELinux property_contexts 校验（模块 15.3）；getprop/setprop 命令排查
      • ·
        ueventd 设备节点
        init 子进程 ueventd 监听内核 uevent（热插拔）→ 按 ueventd.rc 规则创建 /dev/* 节点与权限（/dev/ttyUSB0、/dev/video0、/dev/can0 等）；与 file_contexts 的 SELinux label 联动（模块 15.3/17.1）；驱动节点缺失先查 ueventd.rc
      • ·
        启动阶段 (boot sequence)
        on early-init → init → late-init → post-fs → post-fs-data → zygote-start → boot；与 SystemServer 的 boot phase 对应（模块 2.5）；boot_progress_* 打点贯穿各阶段（模块 1.6）；车载定制在此插桩自定义 rc 阶段
      • ·
        SELinux 启动集成
        init 早期装载 sepolicy（编译进 ramdisk/system）→ 按 cmdline androidboot.selinux 决定 enforcing/permissive → restorecon 恢复文件上下文（模块 15.3）；策略加载失败 → panic 拒启；/sys/fs/selinux/enforce 运行时切换

      1.3 Zygote 孵化器 frameworks/base/core/java/com/android/internal/os/ZygoteInit.java
      • ·
        ZygoteInit.main()
        ZygoteInit.main() 先 registerZygoteSocket() 再 preload：preloadClasses()（frameworks/base/preloaded-classes，约 4000+ 类）+ preloadResources()（framework-res 资源/主题）+ preloadSharedLibraries() + native preload；preload 期间屏蔽 GC；fork 后所有 App 进程经 COW 共享这些预加载页
      • ·
        forkSystemServer()
        fork 出 SystemServer 进程，Zygote 自身进入 runSelectLoop() 等待 fork 请求
      • ·
        Zygote Fork 模型 核心
        App 进程通过 Socket 请求 Zygote fork，子进程继承预加载资源，避免每个 App 重复加载 → 启动加速
      • ·
        Zygote Socket 通信 补全
        App 侧 ZygoteProcess.openZygoteSocketIfNeeded() 建 LocalSocket → 传输 fork 参数（pid/uid/gids/capabilities/class）→ Zygote 侧 ZygoteConnection.runOnce() 解析并 forkAndSpecialize
      • ·
        预加载清单与 COW 继承
        preloaded-classes（约 4000+ 类）+ framework-res 资源在 Zygote 进程预加载；fork 采用写时拷贝 COW：子进程共享物理页，修改才复制 → App 冷启动免重复加载公共类；优化：精简 preloaded-classes 可减内存但增冷启动（谨慎）
      • ·
        forkAndSpecialize 参数
        --setuid/--setgid（uid/gid）· --nice-name（进程名，ps 可见）· --seinfo（SELinux appdomain 域，模块 15.3）· --runtime-args（ART 参数）· --target-sdk-version（兼容行为）；App 进程走 forkAndSpecialize，SystemServer 走 forkSystemServer
      • ·
        UsapPool 进程池 (AOSP 11+)
        Zygote 预 fork 的 Unspecialized App Process 池：App 启动直接取用 → 省 fork 开销 → 冷启动提速；usap_pool_enabled 属性控制（Android 12+ 默认开）；车载开机 KPI 优化依赖（模块 1.6）
      • ·
        Zygote 崩溃与重启策略
        zygote 崩溃 → init onrestart 重启 zygote → 所有 App 进程被杀（无 zygote 无法 fork，桌面重启）；logcat 查 Zygote 崩溃栈；车载低内存防 zygote 被 LMK 误杀（oom_adj 保护，模块 9.3）
    • ▶
      1.4 SystemServer 进程入口 frameworks/base/services/java/com/android/server/SystemServer.java
      • ·
        Zygote fork 后
        ZygoteConnection → forkAndSpecialize → SystemServer.main()
      • ·
        主线程初始化
        Looper.prepareMainLooper → 创建 SystemContext → 加载 framework-res

        forkSystemServer 内部

        boot_progress 打点
        boot_progress_start → boot_progress_system_run → boot_progress_ams_ready → boot_progress_enable_screen 等；logcat | grep boot_progress 定位各阶段耗时（模块 18.5/1.6 联动）；车载开机 KPI 分析主用

        开机完成标志与桌面首帧
        AMS 发完 BOOT_COMPLETED 后置 sys.boot_completed=1 → bootanimation 退出（模块 1.5）→ Launcher 可交互（模块 4）；getprop sys.boot_completed 检查；桌面首帧 = 用户感知开机完成

      1.5 开机动画与 Logo 定制 (bootanimation) 补全 frameworks/base/cmds/bootanimation/ · vendor 侧 logo 资源
      • ·
        开机 Logo（Bootloader / Kernel）
        lk/aboot 显示 logo（vendor bootloader 工程定制，U-Boot logo 同理）；kernel 阶段 fbcon / DRM splash（drivers/video/logo/）；车载/工控整机 logo 定制常改这两处 + splash screen API
      • ·
        BootAnimation 机制
        /system/bin/bootanimation 进程由 SurfaceFlinger 触发（sys.boot_completed 置位前循环播放）；zip 包结构：desc.txt + part0/part1 帧图；bootanimation_main.cpp 解析 desc.txt 驱动播放
      • ·
        定制要点
        生成 bootanimation.zip（分辨率按屏算，建议 1080p/720p 等比缩放）；desc.txt 参数：fps（帧率）· p 1 0 part0（循环次数 1=循环）· 分 part0 循环 + part1 收尾；vendor 目录覆盖 /system/media/bootanimation.zip；缩短动画时长提升开机 KPI
      • ·
        踩坑
        zip 必须 store 存储（勿压缩，否则解压慢卡动画）；分辨率不匹配黑边/拉伸；循环次数设错卡在动画；user 版禁止改动画（system 分区只读）；logcat 查 BootAnimation 播放状态

      1.6 启动时序与开机优化 (Boot KPI) 补全
      • ·
        boot_progress 打点体系
        BootReceiver.java + SystemServer BootTimingsTraceLog；关键点：start → systemRun → amsReady → enableScreen；logcat | grep boot_progress · /data/system/boot_time.txt（bootchart 数据）
      • ·
        优化手段
        init 阶段并行（AOSP 12+ parallel 支持）· SystemServerInitThreadPool 并行初始化（模块 2.1）· 延迟非关键服务（模块 2.4）· UsapPool 预创建（模块 1.3）· 预置应用冷冻 Freeze（模块 3.1）· 精简 PMS 扫描（模块 3.5）

    2. SystemServer 启动阶段 frameworks/base/services/java/com/android/server/SystemServer.java
    SystemServer 服务注册与启动时序，决定核心服务何时就绪
    • ▶
      2.1 run() 入口 流程
      • ·
        执行链
        SystemServer.main() → run()：初始化 VM/加载库 → 创建 SystemContext（framework-res 资源）→ 依次调用 startBootstrapServices/startCoreServices/startOtherServices
      • ·
        关键对象
        SystemServiceManager（服务注册与生命周期中枢）· SystemServerInitThreadPool（并行初始化，缩短开机耗时）· 各服务 Handler 线程
      • ·
        线程与看门狗
        主线程负责启动流程；Watchdog 在启动早期注册，监控主线程/关键线程超时（默认 60s，见模块 10.5）；启动阶段卡死先查 Watchdog 日志
      • ·
        启动前准备
        SystemServer 由 zygote forkSystemServer() 进入（模块 1.4）；Process.setThreadPriority(THREAD_PRIORITY_FOREGROUND) 设前台调度；System.loadLibrary("android_servers") 加载 native 库（JNI 注册，模块 9.4）；设置进程名 system_server
      • ·
        启动失败容错
        每个服务启动 try-catch → Slog.wtf（失败不阻断后续服务，尽量启动）；整体异常 → 记录 WTF 继续；Watchdog 在 run() 早期创建并注册主线程监控（模块 10.5）
      • ·
        与 boot_progress 衔接
        boot_progress_start 打点在此触发（模块 1.6）；各 start* 方法内嵌 BootTimingsTraceLog 记录耗时；logcat | grep -E "boot_progress|SystemServer" 定位启动瓶颈
    • ▶
      2.2 startBootstrapServices() 流程
      • ·
        引导顺序
        Installer（installd 代理）→ DeviceIdentifiers → AMS 先实例化（其他服务依赖其 Binder）→ PowerManagerService → Lights → DisplayManagerService → PackageManagerService → SensorService；SystemServer 自身注册为服务
      • ·
        关键点
        PMS 扫描在此阶段（/system/app、/vendor/app、/data/app，模块 3.5），决定开机时长；AMS/ATMS 先建后 start（依赖 Display 就绪）；SensorService 为 native 服务
      • ·
        车载定制
        依赖 PMS/AMS 的核心系统服务在此阶段插入（如车控服务需在桌面启动前就绪）；注意 phase 时序（PHASE_WAIT_FOR_DEFAULT_DISPLAY 前勿依赖屏幕）
      • ·
        Installer / installd 连接
        最先连接 installd（Binder：IVold/Installd，模块 9.3），APK 安装目录/dex2oat 的执行者；先于 PMS（PMS 扫描安装依赖其）；installd 未就绪 → PMS 阶段阻塞
      • ·
        PMS 扫描优化
        APK 解析用 SystemServerInitThreadPool 并发扫描（提速开机）；packages.xml 持久化缓存（重启免全量重扫）；扫描策略/开机耗时见模块 3.5
    • ▶
      2.3 startCoreServices() 流程
      • ·
        服务清单
        BatteryService（模块 20.5）· UsageStatsService（应用使用统计，决定后台限制）· WebViewUpdateService（WebView 更新）· GpuStatsService（GPU 统计）· DockObserver（底座）等
      • ·
        BatteryService 价值
        读取 /sys/class/power_supply/* 发粘性 BATTERY_CHANGED 广播；低电量阈值 → 系统降载（模块 20.5）；车载充电状态/快充协商依赖
      • ·
        与其他阶段衔接
        core 阶段服务不依赖窗口/输入；startCoreServices 结束后进入最重的 startOtherServices（模块 2.4）；BatteryService 在此阶段即发首个 BATTERY_CHANGED，UI 层可提前读电量
      • ·
        UsageStatsService 深度
        应用使用统计（前台时长/活跃度）→ 后台限制/Doze 白名单依据（模块 20.3/5 联动）；dumpsys usagestats 查看；JobScheduler 依赖其判断使用模式
      • ·
        WebView / GpuStats
        WebViewUpdateService：WebView 提供商管理（可独立更新）；GpuStatsService：GPU 使用统计（dumpsys gpu）；两者均为 AOSP 12+ core 阶段新增
    • ▶
      2.4 startOtherServices() 流程
      • ·
        服务清单（数量最多）
        WMS（依赖 AMS/Display）→ InputManagerService（依赖 WMS 焦点）→ NotificationManagerService → LocationManagerService → ConnectivityService → AudioService → BluetoothService → UsbService 等数十个
      • ·
        依赖顺序
        WMS 必须在 AMS 之后（Activity 窗口关联）；Input 在 WMS 后（焦点窗口）；Connectivity 在 NetworkManagement 后；顺序错乱是定制高频坑（模块 10.5）
      • ·
        耗时与优化
        此阶段为开机最耗时段；优化：延迟非关键服务（looper-only）、SystemServerInitThreadPool 并行、boot_progress 打点定位瓶颈（模块 18.5）
      • ·
        启动模式：同步 vs 延迟
        关键服务同步启动（WMS/IMS/NotificationManager）；非关键用 looper-only 模式（仅注册 handler 后异步初始化，主线程不等）→ 显著提速开机；CriticalCodeSection 标记关键段
      • ·
        阶段完成检测
        各服务 onBootPhase() 回调（模块 10.3）在 startBootPhase() 时触发；Watchdog 监控关键服务 ready 标志；阶段卡死先查 Watchdog dump（模块 10.5）
    • ▶
      2.5 systemReady() 流程
      • ·
        触发链
        startOtherServices() 收尾 → mSystemServiceManager.startBootPhase(PHASE_SYSTEM_SERVICES_READY) → AMS.systemReady()；各服务在 systemReady 里做依赖初始化（WMS 恢复窗口、PMS 扫描完成）
      • ·
        systemReady 内部动作
        恢复最近任务（Recents）· 拉起 PERSISTENT 持久应用（如 SystemUI/Telephony）· 发送 HOME Intent 启动 Launcher（模块 4）· 发 BOOT_COMPLETED 广播（分发给所有应用）
      • ·
        定制点
        SystemUI 在 PHASE_BOOT_COMPLETED 前就绪（桌面可见前 UI 就位）；车载预置应用通过 persistent 或开机广播白名单按需拉起；开机 KPI 优化：延迟第三方广播、冷启动预加载（见模块 18.5）
      • ·
        广播与解锁时序
        systemReady 后按序发 USER_STARTED → USER_UNLOCKED（FBE 解密完成，模块 22.2）→ BOOT_COMPLETED；persistent 应用（android:persistent）在此阶段拉起
      • ·
        SystemUI 与桌面衔接
        SystemUI 由 systemReady/PHASE_BOOT_COMPLETED 拉起（模块 13.1）；桌面首帧后置 sys.boot_completed=1（模块 1.4）；车载预置 App 白名单在 BOOT_COMPLETED 后按需启动

      2.6 startApexServices() 流程
      • ·
        背景
        AOSP 11+ Mainline 模块化（模块 26）：APEX 容器内可携带系统服务，经 apexd 激活后由 SystemServer 加载
      • ·
        流程
        扫描 /apex/<name>@<ver>/ 内的 APEX 服务（ApexService）→ 按 manifest 声明注册；服务代码随 APEX 独立升级
      • ·
        定制影响
        APEX 内新增服务需在 apex_manifest.json 声明 + VINTF/SELinux 联动；车载改造注意：APEX 更新需重启生效、签名需与平台一致（模块 26.1）
      • ·
        ApexService 加载细节
        扫描 /apex/<name>@<ver>/ 内 APEX 包 → 加载 apexservice 声明的 Java 服务（apexservice list 查看）→ 注册进 ServiceManager
      • ·
        与 Mainline 联动
        APEX 更新后服务版本变化（模块 26.1）；车载定制注意：系统服务打包 APEX 需平台签名一致 + VINTF 声明；APEX 内服务不可被 SystemServer 直接 import（隔离边界）

      2.7 SystemServer 启动排障 (Bootloop) 补全 踩坑
      • ·
        启动卡死定位
        logcat -b system 看 SystemServer 各 start* 阶段打印（卡在哪一步即哪阶段）；boot_progress 打点（模块 1.6）；Watchdog 60s 超时 dump 到 /data/anr/（模块 10.5）；先看最后一阶段日志
      • ·
        bootloop 与重启循环
        SystemServer 崩溃（未捕获异常/SELinux 拒绝/内存不足）→ zygote 重启 → 循环；定位：logcat -b crash · /data/tombstones/（native）· avc denied（SELinux，模块 15.5）；ro.boot.bootloader 看启动次数
      • ·
        恢复手段
        安全模式（音量键进入，禁用第三方应用）；recovery 刷机（模块 24.3/19.5）；Last Known Good 方案（车载：保留上次正常启动的快照/slot 切换，模块 24.1）
      • ·
        车载快速恢复策略
        AB 槽位自动回滚（模块 24.1）；Watchdog 自定义超时（车载场景放宽/收紧）；启动失败 N 次自动切备份系统；SELinux 只读策略防误改（模块 15.4）；量产必须验证断电/掉电启动

    3. AMS / ATMS / WMS / IMS / PMS 等核心服务 核心 frameworks/base/services/core/java/com/android/server/{am,wm,input,pm}/
    Framework 四大支柱服务，均运行在 system_server 进程，全部基于 Binder 对外暴露
    • ▶
      3.1 ActivityManagerService (AMS) services/core/java/com/android/server/am/
      • ·
        职责
        四大组件生命周期、进程调度、权限管理、内存回收 (LMK 联动)；另含：Activity 启动/任务栈（Task/Recents）、进程冷/热启动、ANR 监控、ContentProvider 进程拉起（模块 6.5）

      • ·

      14.1 Treble 隔离 核心
